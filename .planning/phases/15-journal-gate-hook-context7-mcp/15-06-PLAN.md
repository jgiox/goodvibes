This is the 3RD REVISION of this same plan (15-06). Round 1 fixed CR-01/CR-02/CR-03 (from `15-REVIEW.md`, found in plan 15-05's shipped fix). Round 2 fixed a NEW bug (CR-04/CR-05) the round-1 checker found in round 1's own drafted fix, before it shipped. Round 3 (this revision) fixes a NEW bug (CR-06/CR-07) the round-2 checker found in round 2's own drafted fix — again before it shipped. The plan still closes the same 3 original CR bypasses using the same **option (b)** approach (fail-closed on compound-command-plus-`-C`) as every prior round. What changed in this revision is narrower still: the `TARGETDIR` extraction is now gated behind an explicit confirmation (via `$UNQUOTED`) that a real `-C` flag exists at all, plus a raw-text ambiguity check, before it is ever attempted against raw `$CMD`.

**The 3 original CR bypasses being closed** (all found in `15-REVIEW.md`, unchanged from before):

1. **CR-01 (fail-open on unresolvable `-C` target):** `git -C /tmp commit -am "fix"` from an unstaged repo exits 0 (ALLOWED) because `git rev-parse --absolute-git-dir` failing against a non-repo path was treated identically to "not running inside a git repo, nothing to gate" — a full bypass with a single extra flag.
2. **CR-02 (`-C` extraction not scoped to the commit clause being gated):** a chained command like `git commit -am "fix" && git -C <staged-repo> status` gets routed to the unrelated trailing repo instead of the real (unstaged) target, silently passing.
3. **CR-03 (quoted `-C` paths erased by the earlier quote-stripping step):** `git -C "/path with a space/repoB" commit -am "fix"` has its quoted `-C` argument blanked out by the same quote-stripping pass that removes commit-message content, so `TARGETDIR` resolves empty and the hook falls back to checking its own cwd — reintroducing the ORIGINAL bypass this whole gap-closure chain exists to fix.

**The round-1-drafted bug fixed in round 2 (CR-04/CR-05 — found by the round-1 checker in round 1's own drafted fix, never shipped):** round 1's first draft of Task 2's fix, while correctly solving CR-03 by extracting `TARGETDIR` from the raw, pre-quote-stripped `$CMD` (needed so a quoted `-C` argument survives), ALSO widened the extraction anchor from the original, `git`-prefixed `git[[:space:]]+-C[[:space:]]+` to a bare `-C[[:space:]]+` with no requirement that a literal `git` token immediately precede it. Combined, these two changes meant a commit MESSAGE whose text merely contains something shaped like `-C <path>` — with no real `-C` flag anywhere on the line — would have that message text extracted as `TARGETDIR` and routed to it. Round 2 restored the `git`-prefixed anchor (`git[[:space:]]+-C[[:space:]]+`), fixing CR-04/CR-05, while keeping the raw-`$CMD` extraction source needed for CR-03.

**The NEW bug this revision fixes (CR-06/CR-07 — found by the round-2 checker in round 2's own drafted fix, never shipped):** round 2's fix restored the `git`-prefixed anchor, but still extracted `TARGETDIR` from raw `$CMD` **unconditionally**, without ever first checking whether `$UNQUOTED` (the quote-stripped variable, which reliably distinguishes a real, non-quoted `git -C` flag from message text merely containing that phrase — now blanked away) shows a real `-C` flag exists in the first place. Because the extraction pattern's `.*` prefix is greedy, it matches the LAST `git -C <token>` occurrence in the raw command line — so when a commit message happens to independently contain the literal adjacent phrase "git -C <token>", that occurrence can be extracted instead of (or in place of) a real flag, or extracted when no real flag exists at all:
- `git commit -am "see git -C <other-repo-path> for the fix"` from an UNSTAGED cwd repo (no real `-C` flag anywhere) exits 0 (bypass — the real, unstaged cwd is ignored; the message text's incidental path is checked instead).
- `git commit -am "fix: git -C anchor bypass in journal-gate hook"` from a STAGED cwd repo (no real `-C` flag anywhere) exits 2 (false block — the message text's incidental "anchor" token is wrongly treated as an unresolvable `-C` target).

This is a genuine NEW regression introduced by round 2's decision to extract from raw `$CMD` instead of `$UNQUOTED` — the actual shipped 15-05 hook extracts `TARGETDIR` from `$UNQUOTED`, which already blanks out quoted commit-message text before the anchor regex ever runs against it, so 15-05 correctly BLOCKS the CR-06 scenario and correctly ALLOWS the CR-07 scenario. It is not a pre-existing limitation 15-05 always had; T-15-19 below is corrected accordingly (see the threat model). None of round 2's 20 planned tests exercised a commit message containing an adjacent "git -C" phrase, so "20/20 green" would not have caught this.

**The fix (round 3, this revision):** gate raw-`$CMD` extraction behind a `$UNQUOTED`-based existence check (`HASREALC`), and additionally fail closed if the anchor pattern matches raw `$CMD` more than once (meaning a real flag AND a message-text lookalike both matched — genuinely ambiguous). Concretely, in order:
1. Compute `HASREALC` by testing `$UNQUOTED` for `(^|[[:space:]])git[[:space:]]+-C([[:space:]]|$)` — this is the same check the compound-guard already computes, now captured once and reused.
2. If `HASREALC` is set AND `$UNQUOTED` contains a shell separator (`&&`/`||`/`;`/`|`) — fail closed exactly as the existing compound-guard already does (unchanged behavior/message, still fixes CR-02).
3. If `HASREALC` is set (and not compound): count occurrences of the same anchor pattern against RAW `$CMD` (`RAWCOUNT`). If the count is not exactly 1, fail closed with a new, distinct, actionable message (ambiguous — a real flag and something else both matched the anchor in the raw text). If the count is exactly 1, extract `TARGETDIR` from raw `$CMD` exactly as round 2 already did (double-quoted / single-quoted / unquoted capture groups, unchanged) — this is what still fixes CR-03 (a quoted path with a space is never blanked out, and `RAWCOUNT` counts only the anchor token, not the full argument, so internal spaces in a quoted value never inflate the count).
4. If `HASREALC` is NOT set: `TARGETDIR` stays empty (extraction is skipped entirely) — this is the part that fixes CR-07 (the false block), since a message merely containing "git -C anchor..." with no real flag correctly leaves `TARGETDIR` empty and falls through to the existing cwd-based path. Gating step 3 behind `HASREALC` (rather than running it unconditionally, as round 2 did) is what fixes CR-06 (the bypass): a real flag now must actually exist (per `$UNQUOTED`) before raw-`$CMD` extraction is even attempted, and the `RAWCOUNT` check then additionally rejects the case where the real flag AND a lookalike both appear in raw text.

Neither change reopens CR-01 or CR-02 (unaffected by this gating — CR-01 is the separate `GITDIR`-resolution fail-closed branch, CR-02 is the separate compound-command guard, both untouched), nor CR-03/CR-04/CR-05 (the anchor and extraction-source properties that fix those are unchanged; only the pre-conditions under which extraction runs have changed).

**Chosen approach — fail-closed on compound-command-plus-`-C` and now also on raw-text ambiguity, NOT a fourth regex layer patched into full clause-scoped extraction.** (Unchanged in spirit from prior rounds.) `15-REVIEW.md`'s own root-cause note states plainly: "parsing shell command syntax with sed/grep string surgery cannot robustly reconstruct what a real shell parser (and git's own arg parsing) would do," and explicitly offers two directions: (a) patch all defects into the existing full-`-C`-support design, or (b) fail closed whenever `-C` appears inside a compound command or the value can't be unambiguously isolated, reserving full extraction for the simple single-invocation case already covered by 15-05's Test D/E/F. This plan continues to take **option (b)**, for two independent reasons:

- **HOOK-01 is a locked requirement** (`.planning/REQUIREMENTS.md`, confirmed complete): "`.claude/settings.json` ships a `PreToolUse` hook, implemented as an inline shell command (no separate script file)". `15-REVIEW.md` WR-02 raises extracting the hook to a real script file as the structural fix that would make clause-scoped parsing reviewable — that path is foreclosed by HOOK-01's explicit "no separate script file" wording, so it is not an option here (noted, not silently adopted).
- **Correctly scoping `-C` extraction to "the same clause as the matched commit token" (option a) requires a genuinely new interacting layer**: splitting the command on shell separators BEFORE quote-stripping (to preserve quoted `-C` paths per CR-03) while ALSO identifying which resulting segment contains the `commit` token (to solve CR-02), all inside an already triple-escaped (JSON string -> shell double-quote -> POSIX ERE) one-liner. This exact string has now produced defects in FIVE straight rounds (2 escaping bugs in 15-04, 3 new bypasses in 15-05 while fixing 1, round 1's own draft introducing CR-04/CR-05 while fixing CR-01/02/03, and round 2's own draft introducing CR-06/CR-07 while fixing CR-04/CR-05) — adding a fourth interacting parsing concern is the pattern `15-REVIEW.md` explicitly warns will keep producing new edge cases of the same shape. Fail-closed-on-ambiguity (the `RAWCOUNT` check) is the same philosophy already applied to the compound-command case, extended one step further, rather than a new parsing layer.

Option (b) eliminates CR-02's entire bug class by refusing to guess: if the command is compound (contains `&&`/`||`/`;`/`|` outside quotes) AND contains a `git -C` invocation, the hook blocks with an actionable message rather than attempting to determine which clause the flag belongs to. `-C` is fully resolved (extracted-and-routed, exactly as 15-05 already does) only for the simple, non-compound, single-invocation case with an unambiguous raw-text anchor match — which is exactly the shape of all three of 15-05's own Test D/E/F scenarios (verified below: this plan's fix produces IDENTICAL exit codes to 15-05's for Test D/E/F, zero behavior change there). CR-01 is a small, unconditional, non-regex change: only treat `git rev-parse --absolute-git-dir` failure as "nothing to gate, allow" when NO `-C` was requested at all; if `-C` was requested (and passed the compound check and the ambiguity check), an unresolvable target now blocks.

**Deliberate, documented behavior change (not a regression), NEW in this revision:** a legitimate single `git -C <path> commit -am "<message>"` command whose commit message ALSO happens to independently contain the literal adjacent phrase "git -C <token>" will now fail closed (BLOCKED) as "ambiguous", even though the first occurrence was the real, legitimate flag. This is a new, narrow false-positive surface introduced by the `RAWCOUNT` check, but strictly safer than either alternative failure mode (silent bypass or silent misroute) — see `<threat_model>` T-15-20.

**Deliberate, documented behavior change (not a regression, carried from round 1):** a compound command that happens to contain BOTH a `git commit` and an unrelated `git -C <path>` invocation (in either order, whether or not the `-C` is attached to the commit) will now be BLOCKED rather than silently mis-routed. This is strictly safer than either of the two failure modes it replaces (silent bypass or silent false-block) and matches no documented, tested, or previously-passing usage pattern — see `<threat_model>` T-15-13.
