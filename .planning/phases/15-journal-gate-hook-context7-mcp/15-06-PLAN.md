<objective>
Close 3 NEW critical bypasses (`15-REVIEW.md` CR-01/CR-02/CR-03) found in plan 15-05's own fix for the original `-C` cross-repo bypass. 15-05 correctly closed the original defect (routing `GITDIR`/merge/staged-file checks through a `-C` target when present) but its extraction approach — greedily pulling a `-C <path>` from the whole quote-stripped command line and trusting it unconditionally — introduced three more severe bypasses, all independently confirmed by direct execution against the real shipped hook (not just static reading):

1. **CR-01 (fail-open on unresolvable `-C` target):** `git -C /tmp commit -am "fix"` from an unstaged repo exits 0 (ALLOWED) because `git rev-parse --absolute-git-dir` failing against a non-repo path was treated identically to "not running inside a git repo, nothing to gate" — a full bypass with a single extra flag.
2. **CR-02 (`-C` extraction not scoped to the commit clause being gated):** a chained command like `git commit -am "fix" && git -C <staged-repo> status` gets routed to the unrelated trailing repo instead of the real (unstaged) target, silently passing.
3. **CR-03 (quoted `-C` paths erased by the earlier quote-stripping step):** `git -C "/path with a space/repoB" commit -am "fix"` has its quoted `-C` argument blanked out by the same quote-stripping pass that removes commit-message content, so `TARGETDIR` resolves empty and the hook falls back to checking its own cwd — reintroducing the ORIGINAL bypass this whole gap-closure chain exists to fix, for any repo path containing a space (a realistic case for this beginner-facing project's Windows/OneDrive/macOS users).

**Chosen approach — fail-closed on compound-command-plus-`-C`, NOT a fourth regex layer patched into full clause-scoped extraction.** `15-REVIEW.md`'s own root-cause note states plainly: "parsing shell command syntax with sed/grep string surgery cannot robustly reconstruct what a real shell parser (and git's own arg parsing) would do," and explicitly offers two directions: (a) patch all three defects into the existing full-`-C`-support design, or (b) fail closed whenever `-C` appears inside a compound command or the value can't be unambiguously isolated, reserving full extraction for the simple single-invocation case already covered by 15-05's Test D/E/F. This plan takes **option (b)**, for two independent reasons:

- **HOOK-01 is a locked requirement** (`.planning/REQUIREMENTS.md`, confirmed complete): "`.claude/settings.json` ships a `PreToolUse` hook, implemented as an inline shell command (no separate script file)". `15-REVIEW.md` WR-02 raises extracting the hook to a real script file as the structural fix that would make clause-scoped parsing reviewable — that path is foreclosed by HOOK-01's explicit "no separate script file" wording, so it is not an option here (noted, not silently adopted).
- **Correctly scoping `-C` extraction to "the same clause as the matched commit token" (option a) requires a genuinely new interacting layer**: splitting the command on shell separators BEFORE quote-stripping (to preserve quoted `-C` paths per CR-03) while ALSO identifying which resulting segment contains the `commit` token (to solve CR-02), all inside an already triple-escaped (JSON string -> shell double-quote -> POSIX ERE) one-liner. This exact string has now produced defects in three straight rounds (2 escaping bugs in 15-04, 3 new bypasses in 15-05 while fixing 1) — adding a fourth interacting parsing concern is the pattern `15-REVIEW.md` explicitly warns will keep producing new edge cases of the same shape.

Option (b) eliminates CR-02's entire bug class by refusing to guess: if the command is compound (contains `&&`/`||`/`;`/`|` outside quotes) AND contains a `git -C` invocation anywhere, the hook blocks with an actionable message rather than attempting to determine which clause the flag belongs to. `-C` is fully resolved (extracted-and-routed, exactly as 15-05 already does) only for the simple, non-compound, single-invocation case — which is exactly the shape of all three of 15-05's own Test D/E/F scenarios (verified below: this plan's fix produces IDENTICAL exit codes to 15-05's for Test D/E/F, zero behavior change there). CR-03 is then solved for that same simple case by extracting `-C` from the RAW command text (before quote-stripping) with a pattern that matches either a double-quoted or an unquoted argument, so a path containing a space is never blanked out. CR-01 is a small, unconditional, non-regex change: only treat `git rev-parse --absolute-git-dir` failure as "nothing to gate, allow" when NO `-C` was requested at all; if `-C` was requested (and passed the compound check), an unresolvable target now blocks.

**Verified before writing this plan** (not a guess — full end-to-end execution against hand-built temp git repos, mirroring `15-REVIEW.md`'s WR-04 examples plus 15-05's own Test D/E/F): all 15 pre-existing scenarios plus all 3 new CR regression scenarios were run against the exact JSON-embedded command string given in Task 2's `<action>` below, using the same JSON-payload-over-stdin mechanism the real integration tests use (`sh -c "<hook>"`, JSON on stdin, real `git init` repos). **Deliberate, documented behavior change (not a regression):** a compound command that happens to contain BOTH a `git commit` and an unrelated `git -C <path>` invocation (in either order, whether or not the `-C` is attached to the commit) will now be BLOCKED rather than silently mis-routed. This is strictly safer than either of the two failure modes it replaces (silent bypass or silent false-block) and matches no documented, tested, or previously-passing usage pattern — see `<threat_model>` T-15-13.
