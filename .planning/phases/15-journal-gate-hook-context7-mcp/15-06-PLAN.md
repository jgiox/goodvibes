<objective>
This is a REVISION of this same plan (15-06), made in response to checker feedback identifying a NEW, more severe bypass in the plan's own (never-shipped) Task 2 fix — this revision corrects that defect before any of this plan's tasks have executed. The plan still closes the 3 CR bypasses from `15-REVIEW.md` (CR-01/CR-02/CR-03) found in plan 15-05's fix for the original `-C` cross-repo bypass, using the same **option (b)** approach (fail-closed on compound-command-plus-`-C`) as before. What changed in this revision is narrower: the `TARGETDIR` extraction anchor and the test matrix.

**The 3 original CR bypasses being closed** (all found in `15-REVIEW.md`, unchanged from before):

1. **CR-01 (fail-open on unresolvable `-C` target):** `git -C /tmp commit -am "fix"` from an unstaged repo exits 0 (ALLOWED) because `git rev-parse --absolute-git-dir` failing against a non-repo path was treated identically to "not running inside a git repo, nothing to gate" — a full bypass with a single extra flag.
2. **CR-02 (`-C` extraction not scoped to the commit clause being gated):** a chained command like `git commit -am "fix" && git -C <staged-repo> status` gets routed to the unrelated trailing repo instead of the real (unstaged) target, silently passing.
3. **CR-03 (quoted `-C` paths erased by the earlier quote-stripping step):** `git -C "/path with a space/repoB" commit -am "fix"` has its quoted `-C` argument blanked out by the same quote-stripping pass that removes commit-message content, so `TARGETDIR` resolves empty and the hook falls back to checking its own cwd — reintroducing the ORIGINAL bypass this whole gap-closure chain exists to fix.

**The NEW bug this revision fixes (CR-04/CR-05 — found by the checker in this plan's own drafted fix, never shipped):** the first draft of this plan's Task 2 fix, while correctly solving CR-03 by extracting `TARGETDIR` from the raw, pre-quote-stripped `$CMD` (needed so a quoted `-C` argument survives), ALSO widened the extraction anchor from the original, `git`-prefixed `git[[:space:]]+-C[[:space:]]+` to a bare `-C[[:space:]]+` with no requirement that a literal `git` token immediately precede it. Combined, these two changes meant a commit MESSAGE whose text merely contains something shaped like `-C <path>` — with no real `-C` flag anywhere on the line — would have that message text extracted as `TARGETDIR` and routed to it:
- `git commit -am "see -C <staged-other-repo> for details"` from an UNSTAGED cwd would have exited 0 (bypass — real target's unstaged state ignored, incidental message text checked instead).
- `git commit -am "notes -C /tmp for later"` from a STAGED cwd would have falsely exited 2 (BLOCKED — `/tmp` isn't a resolvable git repo, violating "allows when JOURNAL.md is staged").

None of the first draft's 18 planned tests exercised a commit message containing `-C`-shaped text, so "18/18 green" would not have caught this. The checker independently verified the currently-SHIPPED 15-05 hook does NOT have this bug (it still uses the `git`-prefixed anchor, just against `$UNQUOTED` instead of raw `$CMD`) — this was a regression introduced by this plan's own first-draft fix, not a pre-existing one.

**The fix (this revision):** restore the `git[[:space:]]+-C[[:space:]]+` anchor (requiring a literal `git` token immediately before `-C`, exactly as in 15-05) for the `TARGETDIR` extraction, while STILL extracting from the raw, pre-quote-stripped `$CMD` (not `$UNQUOTED`) so CR-03's quoted-space-path case remains fixed. These two properties are independent and both necessary: extracting from raw `$CMD` fixes CR-03 (a quoted path survives); requiring the `git` prefix on the anchor fixes CR-04/CR-05 (message text with no preceding `git` token can never match). Neither change reopens CR-01 or CR-02, which are unaffected by the anchor — CR-01 is the separate `GITDIR`-resolution fail-closed branch, and CR-02 is the separate compound-command guard that runs (and already blocks) before `TARGETDIR` extraction is ever reached.

**Chosen approach — fail-closed on compound-command-plus-`-C`, NOT a fourth regex layer patched into full clause-scoped extraction.** (Unchanged from the prior round.) `15-REVIEW.md`'s own root-cause note states plainly: "parsing shell command syntax with sed/grep string surgery cannot robustly reconstruct what a real shell parser (and git's own arg parsing) would do," and explicitly offers two directions: (a) patch all three defects into the existing full-`-C`-support design, or (b) fail closed whenever `-C` appears inside a compound command or the value can't be unambiguously isolated, reserving full extraction for the simple single-invocation case already covered by 15-05's Test D/E/F. This plan takes **option (b)**, for two independent reasons:

- **HOOK-01 is a locked requirement** (`.planning/REQUIREMENTS.md`, confirmed complete): "`.claude/settings.json` ships a `PreToolUse` hook, implemented as an inline shell command (no separate script file)". `15-REVIEW.md` WR-02 raises extracting the hook to a real script file as the structural fix that would make clause-scoped parsing reviewable — that path is foreclosed by HOOK-01's explicit "no separate script file" wording, so it is not an option here (noted, not silently adopted).
- **Correctly scoping `-C` extraction to "the same clause as the matched commit token" (option a) requires a genuinely new interacting layer**: splitting the command on shell separators BEFORE quote-stripping (to preserve quoted `-C` paths per CR-03) while ALSO identifying which resulting segment contains the `commit` token (to solve CR-02), all inside an already triple-escaped (JSON string -> shell double-quote -> POSIX ERE) one-liner. This exact string has now produced defects in FOUR straight rounds (2 escaping bugs in 15-04, 3 new bypasses in 15-05 while fixing 1, and this plan's own first draft introducing CR-04/CR-05 while fixing CR-01/02/03) — adding a fourth interacting parsing concern is the pattern `15-REVIEW.md` explicitly warns will keep producing new edge cases of the same shape.

Option (b) eliminates CR-02's entire bug class by refusing to guess: if the command is compound (contains `&&`/`||`/`;`/`|` outside quotes) AND contains a `git -C` invocation anywhere, the hook blocks with an actionable message rather than attempting to determine which clause the flag belongs to. `-C` is fully resolved (extracted-and-routed, exactly as 15-05 already does) only for the simple, non-compound, single-invocation case — which is exactly the shape of all three of 15-05's own Test D/E/F scenarios (verified below: this plan's fix produces IDENTICAL exit codes to 15-05's for Test D/E/F, zero behavior change there). CR-03 is then solved for that same simple case by extracting `-C` from the RAW command text (before quote-stripping) with a pattern that matches either a double-quoted or an unquoted argument, so a path containing a space is never blanked out — and, per this revision, that extraction stays anchored on a literal `git` token immediately before `-C` (same anchor 15-05 always used), so message text alone can never satisfy it. CR-01 is a small, unconditional, non-regex change: only treat `git rev-parse --absolute-git-dir` failure as "nothing to gate, allow" when NO `-C` was requested at all; if `-C` was requested (and passed the compound check), an unresolvable target now blocks.
