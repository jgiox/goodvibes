<objective>
Close the sole remaining BLOCKER gap from `15-VERIFICATION.md` (independently reproduced from `15-REVIEW.md` CR-01, a NEW defect found after plan 15-04 already closed a different, earlier gap): the journal-gate hook's git-state checks (`GITDIR` resolution, the `MERGE_HEAD`/`rebase-merge`/`rebase-apply` exemption checks, and `git diff --cached --name-only`) always run against the hook process's own cwd and never honor a `-C <path>` argument present in the intercepted command text. This produces both a bypass (a commit to an unstaged target repo is wrongly allowed) and a false block (a commit to a correctly-staged target repo is wrongly blocked). `-C` handling was an explicit, named goal during original phase planning (15-CONTEXT.md, 15-01-PLAN.md Test 8: "the `-C` variant must still be caught") — this closes an incomplete implementation of a stated requirement, not new scope.

**Chosen approach — full `-C <path>` support, not fail-closed-on-detection:** 15-REVIEW.md CR-01 offered two options: (1) extract the `-C` target and route every git invocation through it, or (2) fail closed (always block) whenever `-C`/`--git-dir=`/`--work-tree=` is detected, if full support is judged too risky. This plan takes option (1) because this gap's own mandated test scenario — cwd unstaged, `-C` target staged, must ALLOW (exit 0) — cannot be satisfied by a fail-closed policy: any policy that blocks on `-C` detection alone would incorrectly block that required scenario. Only routing the checks to the actual target directory satisfies both mandated directions (block when the real target is unstaged, allow when it is staged), so full `-C` support is the only approach that passes the test scenarios named in `15-VERIFICATION.md`.

**Revision note (this plan was revised once by gsd-plan-checker before execution):** the first draft of this plan's Task 2 command extracted `TARGETDIR` and routed the `GITDIR`/`GIT()`-wrapper machinery through it, but resolved `GITDIR` via the relative form `git rev-parse --git-dir` (which, per `git rev-parse` semantics, returns a path relative to the invocation cwd — typically the literal string `.git` — when `-C` is used, not an absolute path). The three subsequent exemption checks (`[ -f "$GITDIR/MERGE_HEAD" ]`, `[ -d "$GITDIR/rebase-merge" ]`, `[ -d "$GITDIR/rebase-apply" ]`) are plain POSIX file-test operators, not routed through the `GIT()` wrapper (routing a file-test operator through a `git -C` subcommand makes no sense — there is nothing to invoke `git` for), so they always resolved `$GITDIR` against the hook process's own actual cwd, not `$TARGETDIR`. Empirically reproduced against real hand-built repos: cwd=repoA (not mid-merge, staged), `-C` target=repoB (mid-merge, `MERGE_HEAD` present, unstaged) -> the draft command returned exit 2 (false block) instead of the required exit 0 (merge exemption). **Fix:** use `git rev-parse --absolute-git-dir` (available since Git 2.13; confirmed present in this environment's Git 2.43.0) instead of `git rev-parse --git-dir`, so `$GITDIR` is always an absolute path regardless of `$TARGETDIR`, and the plain file-test checks resolve correctly no matter what the hook process's own cwd happens to be. This is the only line that changed from the first draft; `TARGETDIR` extraction, the `GIT()` wrapper itself, and every other line are unchanged. The corrected command was re-verified end-to-end (not just the one line in isolation) against all 15 scenarios below (12 pre-existing + Test D + Test E + Test F) in fresh hand-built temp repos before being written into this plan; see Task 2's `<action>` for the exact re-verified string.

**Test F methodology note:** the gap-closure feedback that prompted this fix specified Test F as: cwd NOT mid-merge with JOURNAL.md **staged**, target mid-merge with JOURNAL.md unstaged, expect exit 0. Empirically running that exact scenario against the currently-shipped (pre-this-plan) hook — which has no `-C` awareness at all and evaluates every check against the hook's own cwd — showed it *already* returns exit 0 (cwd's own staged-file check happens to pass), for a completely different, wrong reason (it never even looks at the target's merge state). That version of Test F would not be RED at Task 1's checkpoint, silently defeating the RED->GREEN verification this gap-closure round exists to provide. This plan instead sets the cwd's `JOURNAL.md` to **unstaged** (not staged) in Test F: empirically confirmed this version genuinely fails (exit 2, wrongly blocked) against both the currently-shipped hook and the first draft's buggy relative-`--git-dir` command, and genuinely passes (exit 0) only against the corrected `--absolute-git-dir` command — i.e., it is a real RED->GREEN test for the exact defect this plan fixes, testing the identical claim (target's merge-in-progress state, not the hook's cwd's merge state, is what must be honored) with a materially stronger, non-coincidental signal.

**Scope boundary for this fix:** only `-C <path>` is parsed and honored, matching the exact flag named in the original phase's goal (15-01-PLAN.md Test 8) and in both of this gap's required test scenarios. `--git-dir=`/`--work-tree=` are explicitly NOT parsed by this fix (documented as an accepted limitation in `<threat_model>` T-15-09, mirroring the T-15-05 precedent from plan 15-04) — adding two more capture-group branches to an already fragile triple-escaped one-liner (15-REVIEW.md WR-02) for flags neither named in the original goal nor exercised by either required test scenario is out of scope for this gap-closure round.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-08 | Tampering | `TARGETDIR` extraction / `GIT()` wrapper / `GITDIR` resolution (the exact bug this plan fixes) | mitigate | Extract a `-C <path>` argument from `UNQUOTED` via an anchored `sed -nE ... p` capture group (empty string if absent); route `GITDIR` resolution — via `git rev-parse --absolute-git-dir`, not the relative `--git-dir` — the `MERGE_HEAD`/`rebase-merge`/`rebase-apply` exemption checks, and the staged-file diff through `git -C "$TARGETDIR"` when present via the `GIT()` wrapper function. Using the absolute form is required because the plain `[ -f "$GITDIR/..." ]` file-test checks are not (and cannot meaningfully be) routed through `GIT()`, so a relative `GITDIR` value resolves against the hook process's own cwd rather than the target — this exact gap was caught by plan review before merge and is why `--absolute-git-dir` is used instead of `--git-dir`. Closes CR-01's cross-repo bypass (unstaged target wrongly allowed), false-block (staged target wrongly blocked), and target-merge-exemption false-block (target mid-merge state ignored) in all three directions; verified against all three new adversarial scenarios plus all 12 pre-existing scenarios in hand-built temp repos before being written into this plan |
| T-15-09 | Tampering | `--git-dir=`/`--work-tree=` flags (deliberately NOT parsed by this fix) | accept | Only `-C <path>` is extracted and honored. A commit issued with `--git-dir=`/`--work-tree=` instead of `-C` is still checked against the hook's own cwd — same class of defect as CR-01, undiminished for those two flags. | T-15-10 | Injection | `$TARGETDIR` (attacker/model-controlled path text) passed to `git -C "$TARGETDIR"` | mitigate | `$TARGETDIR` is always double-quoted in the `GIT()` wrapper (`git -C "$TARGETDIR" "$@"`), so it cannot be word-split or glob-expanded into extra arguments.
